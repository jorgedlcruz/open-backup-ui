# v1.2.0 validation and release readiness

This report accompanies the [release notes](v1.2.0.md) and [PR description](v1.2.0-pull-request.md). It compares `features/v1.2.0` with v1.0.1 and separates implementation checks from real recovery outcomes.

## Readiness

The candidate is **ready for PR review**. The final full suite passed **1,275 tests**, with no failures or skips, and the production build passed compilation, lint, TypeScript and page generation. The existing preview on port **3124** now runs that candidate. Clean CI and the operator acceptance tests below remain before publication.

Final QA found and fixed four reliability issues: slow single-workload starts losing their acknowledgement, completed SQL operations disappearing from the active-operation response, stale-lock races permitting duplicate native dispatch, and missing kiosk-launcher dependencies in standalone packaging. The added regression cases cover interrupted responses, reloads, concurrent workers and late validation results.

The release documentation is a draft for review. No remote PR, tag, GitHub Release or deployment to the main application is created by this preparation.

## Publication checklist

- [ ] Review the PR and release notes, including private Web UI API dependencies and supported-method boundaries.
- [ ] Run the repository's GitHub validation workflow on the proposed commit (Node 20 and 22, clean dependency installation, tests, file versions and production build).
- [ ] In a disposable lab, confirm the desired recovery paths with real outcomes: a multi-VM group, migration and publication cleanup, guest-file Keep/Overwrite, NAS copy, and the AD/SQL restore methods intended for use. Existing browse tests do not substitute for these writes.
- [ ] If Windows volume recovery is part of the release acceptance scope, verify it with the connected recovery appliance and disposable destination disks.
- [ ] Review the development dependency advisory and any new advisories reported by CI.
- [ ] Publish only after the reviewed commit is selected. Pushing a `v*.*.*` tag triggers the repository's release workflow, which creates the GitHub Release and source/Linux standalone artifacts.

The local main application on port 3000 remained on its original process throughout QA. Only the existing preview on port 3124 was updated.
