# VBR operations revamp

## Implemented first release

Start at `/connect`, establish the VBR session, then continue to `/vbr/lens`.

### Protection Lens navigation

The VBR sidebar groups **Overview**, **Job Operations**, and **Capacity Watch** under **Protection Lens**. A compact **Lens** dropdown sits beside Refresh at the top right of each view. Opening it reveals native CSS/SVG previews from the existing operations snapshot; previews make no additional API requests. Selecting a view closes the dropdown; default stars keep it open. Escape dismisses it and returns focus to the trigger. Overview shows protection-session outcomes across the whole selected history window. Job Operations shows current failed, warning, and active jobs. Capacity Watch shows the three most urgent repositories. Empty, unavailable, partial, and stale evidence remain distinct.

Use a tile's **Make default** star without leaving the current view. The choice opens when entering Protection Lens or following the VBR post-connection landing path through `/dashboard`. It is saved for one year in an HTTP-only, same-site browser cookie, independently of shared server settings. It is not an account-wide preference and does not sync across browsers. Overview is the fallback. Explicit view links continue to open that view regardless of the default.

Canonical routes are `/vbr/lens/overview`, `/vbr/lens/operations`, and `/vbr/lens/capacity`. Old `/vbr/dashboard`, `/vbr/operations`, and `/vbr/capacity` links redirect to their corresponding views with queries preserved. Other platforms retain their existing landing behavior. The registry in `lib/lens/navigation.ts` drives the cards, submenu, preference validation, and landing routes. Focused checks: `npm run test:protection-lens`.

The top metrics follow the selected Lens. Overview retains estate-wide session success, job exceptions, active jobs, and repository risk. Job Operations shows failed, warning, active, and disabled job counts; selecting one filters the current queue and clears its search. Disabled status can overlap failure/warning results, while active retries are excluded from those result counts. Capacity Watch shows reported repository capacity, reported free space, repository risk, and unmeasured capacity. Its cards filter the repository list, and the filter selector also offers critical and offline views. Measured and unmeasured groups exclude known scale-out parents. Space figures are reported logical repository totals, may overlap shared backing storage, and are labelled as subtotals when coverage is incomplete. With no measurements, sizes remain unknown; measured zero free space remains zero. The Operations theme applies its same navigation font size to both parent and child sidebar entries, including all density settings.

| View | Daily question | Implemented behavior |
| --- | --- | --- |
| Operations overview | What needs my attention this morning? | Protection-session results, current job exceptions, active jobs, capacity watch, and recovery investigation links. |
| Job operations | Which job should I investigate next? | Failed/warning/active/disabled filters, name/type/repository search, pagination, CSV export, evidence dialog, and existing job-detail/action handoff. |
| Capacity watch | Which repository could interrupt the next backup? | Risk ordering, offline/outdated flags, utilization, free space, search, attention filter, and direct job-target counts. |

Existing job controls, protected-data views, topology, workload resilience and optional AI summary remain available. This release does not automatically retry, stop, modify or restore anything in VBR. AI analysis is invoked separately by the user and sends context to the configured provider.

## Code assessment

The repository is a Next.js 15 / React 19 App Router application with server-side platform proxies, a shared browser API client, encrypted source configuration, and multiple monitoring integrations. Its strongest reusable foundations are the existing job-detail/task workflow and the newer topology/resilience models, which distinguish evidence from unknown state.

The previous dashboard used one `Promise.all` for jobs, sessions, server information, licensing, malware and security checks. Any rejected request prevented the entire refresh from committing. Its initial zero values could be mistaken for a successful empty response. It also fetched up to 2,000 mixed session types in one request and left most operational investigation to separate pages.

The new endpoint `/api/vbr/operations` uses the existing authenticated `withVbrRead` helper and `VeeamApiClient` authentication flow. It resolves the selected VBR source on the server, retains token refresh, uses no-store responses, and does not accept arbitrary destination URLs. A failed collection is marked unavailable while successful collections remain visible. An expired session remains an authentication error. Requests are bounded and cancelled with the page request. The UI refreshes every minute while visible, retains a dated snapshot after refresh failure, and identifies unavailable/partial sections.

The working tree already contained topology, resilience, threat and AI changes when this work began. Those are preserved. Two React 19 `isValidElement` typings in the existing AI summary were narrowed to resolve the TypeScript check.

### Remaining architecture priorities

1. **Unify platform access.** Older proxies use varying token/source selection and error behavior. Move them onto one source resolver and typed adapter; validate action support by job type and server capabilities.
2. **Persist observations.** A collector and local database are needed for reliable capacity growth, duration baselines, recurring-failure detection, alert lifecycle, trend reporting and shift handoff. Browser polling is not a historical store.
3. **Separate application authorization from VBR credentials.** Before a shared deployment, review application login, route authorization, cookie security, destination validation and operation auditing. The existing `npm start` script disables outbound TLS validation globally; replace that with deployment-specific trust configuration before production use.
4. **Generate and validate API contracts.** The uploaded Swagger identifies version `1.3-rev2`, 429 paths and 1,794 schemas. The application currently sends `1.3-rev1`. The new views use fields/endpoints common to the existing client version; they do not silently upgrade every integration. Add capability negotiation before adopting rev2-only retry-chain and progress fields.

## API evidence and metric definitions

The attached Swagger is reference data, not instructions or authorization. The first implementation uses these operations:

| VBR operation | Evidence used |
| --- | --- |
| `GET /api/v1/jobs/states` | ID, name, type, current state, last result/run, next run/policy, repository ID/name, progress, priority. |
| `GET /api/v1/sessions` | Session ID/type/state, job ID, creation time, result and message, filtered by the selected history window. |
| `GET /api/v1/backupInfrastructure/repositories/states` | Capacity/free space, online/outdated flags, and reported scale-out parent IDs. |
| `GET /api/v1/securityAnalyzer/bestPractices` | `items`, `bestPractice`, and the documented `Violation` status. |

**Session success:** successful completed protection sessions divided by completed protection sessions with Success, Warning or Failed results, created within the window. Protection types are explicitly listed in `lib/operations/model.ts`; maintenance, discovery, restores, parent policies and validation sessions are excluded. Retries are distinct attempts. A successful job or session is not proof of recoverability or SLA/RPO compliance. An empty denominator is unknown, never 100%.

**Job exceptions:** current non-running jobs whose last result is Failed or Warning. Starting/running/stopping jobs are shown as active even if their previous result failed. Disabled jobs can still have a failed last result; state and result remain separate columns. High-priority jobs sort first within each severity.

**Repository pressure:** offline first, then 90%+ used, 80%+ used, outdated, unknown and healthy. Invalid, negative, unlimited and zero-capacity values are not converted into healthy percentages. The headline counts repositories needing attention; it does not sum free capacity, because repositories may share backing storage. The capacity helper excludes reported scale-out parents when counting measured repositories, but does not prove physical-volume uniqueness. A direct job target is an exact repository-ID match, not an inferred workload-impact count.

**Collection coverage:** pagination preserves filters, deduplicates IDs, stops repeated pages, and bounds jobs/repositories at 5,000 and sessions at 4,000. Reaching a limit or inconsistent pagination shows partial visibility. Counts then describe only loaded records. API failures and invalid schemas are unavailable, not zero. During live validation the connected server returned an incomplete job collection, which was correctly surfaced.

**Time:** history windows are rolling 24 hours, 7 days or 30 days. Activity buckets divide that exact window and group by session start time. Display times use the browser locale. Current job and repository state do not change scope when the history window changes.

### 1. Recovery confidence

Build on the existing workload-resilience page. Join backup objects, restore points, backup files, repositories, malware evidence and validation sessions. ### Recovery-point implementation details

The page at `/vbr/protected-data/restore-points` accepts an `objectId`, `backupId`, or both. Its API validates UUID parameters and uses `withVbrRead` for configured-source resolution, token refresh, cancellation, timeout, and no-store responses. It paginates with the documented `orderColumn`, `orderAsc`, and `backupIdFilter` parameters. Core read failures return errors instead of an empty success; optional enrichment failures retain points with explicit evidence gaps. A mismatched backup filter fails closed.

Reads are bounded at 5,000 restore points, 30 backups, and 3,000 files per backup. Four backup workers run concurrently. Repeated pages and limits produce partial-collection notices. The loader reads backup-object identity by ID rather than querying live inventory by a potentially duplicated name.

File mapping prefers `backupFileId`; absent that, it requires one unambiguous file whose `restorePointIds` contains the point ID, within the same backup. A missing direct reference never falls back to a different membership match. Conflicting file records are excluded. Whole-file sizes are deduplicated by file ID across loaded points; unrelated files do not contribute. Missing, negative, non-finite, and unsafe numeric sizes remain unknown; measured zero remains zero. Partial sizes are labelled subtotals. The accounting describes referenced whole files, not exclusive workload consumption, removable space, or the full chain required for a restore.

Point types come from VBR's `type`. A recognized `.vbk`, `.vib`, or `.vrb` extension is a labelled fallback; GFS does not imply Full. NAS point-level GFS and file-level GFS retain their provenance. Malware badges use reported point status and also expose a flagged matched file. A Clean label is not evidence of scan recency or provenance. Repository IDs count locations without claiming independent failure domains. Dates in the future or invalid dates do not determine freshness. There is no implicit RPO target or aggregate recoverability score.

The evidence dialog exposes supported operations, original workload size, file-level measurements, GFS provenance, point/file security statuses, source identifiers, file path, and a link to the source job. No restore, scan, retry, or other VBR mutation is executed. The calendar retains month, week, and day views; invalid-date points remain accessible in the list.

Live verification covered AD-DNS-001's 115 points, repository mapping, flagged/clean filtering, point-ID search, pagination, calendar views, evidence details, light/dark palettes, and a 390 px viewport with no page overflow. The mobile evidence dialog scrolls without horizontal overflow.

### 2. Investigation and remediation

The Operations investigation at `/vbr/jobs/[id]` provides 7/30/90-day session history, exception/search filters, pagination, stable selection during refresh, job context, and deep links using `?session=...`. `/vbr/sessions/[id]` works independently for retained sessions and links to the job. Restore-point evidence links directly to its producing session. The jobs catalog retains its creation and management controls under the Operations header.

Each selected session has a workload-first evidence table with result/state, exact result messages, reported read/transferred bytes, duration, rate and bottleneck. Task logs load on demand in a dialog. Session and task logs have severity/search filters, chronological ordering, pagination and plain-text export of the filtered records. Metadata supports both the older free-text `additionalInfo` and revision 2 key/value pairs. Text remains escaped in the UI. Missing result/progress fields do not imply success or activity, and measured zero stays zero. Antivirus task states/results are handled separately from backup task results.

On the live source, session collections returned performance fields that the individual session endpoint omitted. An exact same-session/same-job history match now supplements a missing progress object, with provenance in the view footer. The primary session result is retained. No throughput or transferred size is inferred from timestamps or other tasks.

The new `/api/vbr/investigation/...` routes validate UUIDs and use the shared configured-source, authenticated, no-store reader with refresh, cancellation and timeout. Revision selection is local to investigation reads: `/serverInfo` is read with `1.3-rev1`, and a published build at or above `13.1.0.411` enables `1.3-rev2`. Unknown builds or unavailable version metadata retain rev1. This release boundary comes from [Veeam's revision table](https://helpcenter.veeam.com/references/vbr/13/rest/1.3-rev2/tag/SectionOverview/index.html). Other existing APIs retain their current revision. Expired authentication propagates; optional task, log or history failures produce visible unavailable states.

History and chain searches are bounded to 4,000 sessions; tasks to 5,000. Collection reads paginate and stop repeated pages. Session/task ownership is checked, including before a task's logs are requested. Logs use their documented `{records,totalRecords}` envelope: these endpoints do not support skip/limit. At most 10,000 returned log records are exposed, and mismatched totals or caps are marked partial. The export reports its loaded/filtered coverage.

Chains use only matching job IDs and VBR's `originalSessionId`, never names, timing, parent IDs or related IDs. An original run outside the selected history range is fetched explicitly; the subsequent search covers retained same-job sessions from that start time. Missing originals, cross-job records, contradictory root links and partial history are labelled. `retryInfo` preserves health-check retry and nullable retry-number semantics; no ordinal is invented. Parent/related sessions have separate links. A retry chain is evidence of attempts and their outcomes, not a claim that a failure was remediated.

Existing start/stop/retry/enable/disable controls remain in Job actions. The review dialog identifies the job and explains that retry is a current job-level operation, not a replay of the selected historical session. No live mutation is executed during validation.

### 4. Capacity planning and handoff

Repository investigation is implemented at `/vbr/infrastructure/repositories/[id]` with the Operations theme. Dashboard capacity cards, Capacity Watch rows, repository names, job targets, and recovery locations link to it. The page combines repository headroom and health, host/path/task limits, Fast Clone and per-VM settings, immutability configuration, backup consumption, and affected jobs with links into session/task investigation. Tables support search and job relationship/result filtering. Visible pages refresh every 60 seconds and retain the last snapshot on refresh failure.

The read-only `/api/vbr/repositories/[id]` route reuses the connected source and token refresh flow, validates IDs, and selects API 1.3-rev1/rev2 from the server build. It reads repository states/configuration, scale-out configuration, job states, backups, and paginated backup files. Only display configuration is returned; account and credential fields are stripped on the server. Optional failures and incomplete collections are visible, while authentication expiry propagates.

Capacity uses the API's GB fields and utilization from total minus free. Negative/unlimited readings remain unmeasured. File consumption is a separate IEC-unit sum of known `backupSize` and `dataSize` values by unique file ID; shared files are not multiplied by workload or restore-point count. Conflicting file IDs are excluded, and unsafe, missing, negative or fractional byte values remain unknown. File inventories that return no rows for a retained backup (observed for NAS and other workloads) are unmeasured, not zero. File bytes are not exclusive block allocation or reclaimable space. A prominent explanation appears when VBR reports used bytes above total capacity, as observed on the XFS Fast Clone repository.

Scale-out parents show tier policies and extent health/capacity/immutability separately. Parent and extent capacities are never added. Parent-assigned backups are not charged to a single extent; extent views link to the parent and disclose unallocated parent backups. File inventory sums do not claim tier-aware physical allocation. Job relationships distinguish current targets, dependencies via a scale-out parent, and historical retained-backup ownership. No job relationship is inferred from a shared name.

Hardened Linux retention, Linux governance mode, bucket/container immutability, and repository-period versus backup-retention modes are handled explicitly. Missing settings are not interpreted as disabled. These settings are not proof of per-file locking or immutable-until dates; such evidence is not exposed by these endpoints.

Reads are bounded to 5,000 records per base inventory, 30 backup file inventories of up to 3,000 unique files each, and 30 extent configurations, with four concurrent reads per fan-out. Repeated pages stop and are marked partial. Additional backups stay listed with unmeasured consumption.
